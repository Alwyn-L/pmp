## 一、每日巡检（每个工作日 09:00 前，约 10 分钟）

| # | 检查项 | 命令 | 通过标准 |
|---|---|---|---|
| 1 | 容器运行与健康 | `docker compose --env-file .env ps` | 全部 `Up`；`healthy`；`minio-init` 为 `Exited (0)` |
| 2 | 部署自动验证 | `bash scripts/verify.sh` | 失败项 0 |
| 3 | 入口可用性 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:${HTTP_PORT:-8080}/` | `200` |
| 4 | 依赖链路 | `curl -s http://127.0.0.1:${HTTP_PORT:-8080}/api/v1/dependencies` | `"overall":"UP"` |
| 5 | 资源占用 | `docker stats --no-stream` | 内存 < 上限 80%，CPU 无持续打满 |
| 6 | 宿主磁盘 | `df -h /data` | 可用 > 20% |
| 7 | 备份结果 | `ls -lh backups \| tail -5` | 当日备份存在且大小合理 |
| 8 | 近 24h 错误日志 | `docker compose --env-file .env logs --since 24h backend \| grep -c ERROR` | 无持续增长的错误簇 |
| 9 | 容器重启次数 | `docker inspect -f '{{.Name}} {{.RestartCount}}' $(docker compose --env-file .env ps -q)` | 无新增重启（>2 需追查） |
| 10 | 关键告警 | Grafana / 告警通道 | 无未确认的 P1/P2 告警 |

## 二、每周巡检

| # | 检查项 | 命令 | 说明 |
|---|---|---|---|
| 1 | 镜像与基础镜像漏洞 | `docker scout cves pmp/backend:${tag}` 或私服扫描报告 | 高危漏洞 7 天内修复 |
| 2 | 日志保留有效性 | Loki 查询 7 天前日志应为空 | 超过保留期仍存在需检查 compactor |
| 3 | 备份可恢复性抽检（每月至少 1 次） | 在演练库执行 `restore.sh pg` | 记录恢复耗时，更新 RTO |
| 4 | 证书到期（如有 HTTPS） | `openssl x509 -enddate -noout -in cert.pem` | 到期前 30 天续期 |
| 5 | 数据量增长 | `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c "select pg_database_size(current_database())/1024/1024 as mb;"` | 环比增长 < 20% |
| 6 | Redis 内存与淘汰 | `docker compose exec redis redis-cli -a $REDIS_PASSWORD info memory` | `used_memory` < `maxmemory` 的 80% |
| 7 | Kafka 堆积（如已接入业务） | `docker compose exec kafka kafka-consumer-groups --bootstrap-server localhost:9092 --describe --all-groups` | LAG 无持续增长 |
| 8 | MinIO 容量 | `docker compose exec minio sh -c "du -sh /data"` | 低于磁盘 70% |
| 9 | `.env` 与文档一致性 | 人工核对镜像 tag、端口 | 与变更记录一致 |

## 三、每月运维动作

1. 全量备份归档到异地（`rclone sync`），核对校验和。
2. 演练一次**故障恢复**：执行 `docker exec pmp-backend-1 kill -TERM 1`，确认 `RestartCount` 递增并恢复 `healthy`；**不要用 `docker kill` 做演练**（Docker 29+ 视作主动停止，不触发重启）。在测试环境演练一次数据恢复。
3. 容量评审：CPU/内存/磁盘/数据库增长趋势，提前 30 天给出扩容建议。
4. 依赖版本评审：基础镜像与中间件是否有安全补丁，记录是否升级。
5. 清理：`docker image prune -f`、`docker builder prune -f --filter until=168h`、过期备份。
6. 账号与密钥：核查 Grafana/MinIO 账号，轮换到期口令（轮换后必须重建相关容器）。

## 四、告警阈值与分级

| 级别 | 触发条件 | 响应时限 | 处置 |
|---|---|---|---|
| P1 | 入口不可用；`/api/v1/dependencies` 非 UP 超过 3 分钟；数据库不可用 | 5 分钟 | 立即介入，必要时回滚 |
| P2 | 5xx 比例 > 1% 持续 10 分钟；容器反复重启；内存 > 90% | 15 分钟 | 定位根因，观察或扩容 |
| P3 | 磁盘 > 80%；日志量异常；备份失败 | 1 小时 | 当日处理 |
| P4 | 单次告警、自动恢复 | 次工作日 | 记录并跟踪 |

## 五、故障处置流程

```
发现告警/巡检异常
   │
   ├─ 1. 判定影响面：入口是否可用？影响哪些业务域？
   ├─ 2. 保留现场：docker compose ps / logs --since 30m / docker stats
   ├─ 3. 快速恢复优先：重启容器 → 回滚镜像 tag → 切备用链路
   ├─ 4. 定位根因：按第六节故障树逐项排除
   ├─ 5. 记录：故障时间线、根因、处置动作、改进项（24h 内提交）
```

**通用三件套**

```bash
docker compose --env-file .env ps
docker compose --env-file .env logs --since 30m --tail=300 <service>
docker stats --no-stream
```

## 六、故障树（按现象定位）

### 6.1 页面打不开 / 502 / 504

```bash
docker compose --env-file .env ps frontend backend
docker compose --env-file .env logs --tail=100 frontend
docker compose --env-file .env exec frontend wget -qO- http://backend:8080/api/v1/ping
ss -lntp | grep -E ':(80|443|8080)\b'      # 本项目入口为 8080
```

| 根因 | 判据 | 处置 |
|---|---|---|
| frontend 未就绪 | `ps` 显示 restarting | `logs frontend` 看模板渲染/nginx 报错 |
| backend 不健康 | backend `unhealthy` | 转 6.2 |
| 端口被占用 | `ss` 显示其他进程 | 停冲突进程或改 `HTTP_PORT`（本机 80/443 已被 Dify 占用） |
| 上游解析失败 | nginx 日志 `no resolver defined` | 确认模板含 `resolver 127.0.0.11` |
| 重启后短暂 502 | backend 刚重启、Spring Boot 未就绪 | 等 30~60s 重试；持续 502 转 6.2 |

### 6.2 backend 不健康 / 反复重启

```bash
docker compose --env-file .env logs --tail=200 backend
docker compose --env-file .env exec backend wget -qO- http://127.0.0.1:8080/actuator/health
docker compose --env-file .env exec postgres pg_isready -U $POSTGRES_USER -d $POSTGRES_DB
```

| 根因 | 判据 | 处置 |
|---|---|---|
| 数据库连不上 | 日志 `Connection refused` / `password authentication failed` | 核对 `POSTGRES_*`、容器健康 |
| OOM | `docker events --filter event=oom`；退出码 137 | 降低 `MaxRAMPercentage` 或提高内存限额 |
| 只读文件系统写入失败 | 日志 `Read-only file system` | 检查是否往 `/app` 写文件，应写 `/tmp` 或对象存储 |
| 配置项缺失 | 启动日志 `Could not resolve placeholder` | 补 `.env` 变量后 `up -d backend` |
| 手动 `docker kill` 后未自动拉起 | `docker kill` 后状态恒为 `exited`、`RestartCount` 不变 | Docker 29+ 视为主动停止，属预期行为；执行 `docker compose --env-file .env up -d backend` 恢复 |

### 6.3 依赖异常（`/api/v1/dependencies` 单项 down）

| 依赖 | 快速验证 | 常见原因 |
|---|---|---|
| postgres | `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c 'select 1'` | 密码变更未同步、数据卷权限、连接数打满 |
| redis | `docker compose exec redis redis-cli -a $REDIS_PASSWORD ping` | 密码不一致、`maxmemory` 满且写入被拒 |
| kafka | `docker compose exec kafka kafka-broker-api-versions --bootstrap-server localhost:9092` | `CLUSTER_ID` 非法、磁盘满、启动未完成 |
| minio | `docker compose exec minio curl -f http://127.0.0.1:9000/minio/health/live` | 凭据变更、磁盘满、桶未创建 |

> 修改中间件密码必须**同时**更新 `.env` 并重建引用方（backend/redis/minio），否则出现"单侧认证失败"。

### 6.4 数据看不到 / 数据丢失

```bash
docker volume ls | grep pmp_
docker compose --env-file .env exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\dt app.*'
curl -s http://127.0.0.1/api/v1/checks
```

| 根因 | 判据 | 处置 |
|---|---|---|
| 误用 `down -v` | 卷不存在 | 从备份恢复（`restore.sh pg`） |
| 卷挂载错误 | `docker inspect` 中 Mounts 为空 | 修正 compose 后重建 |
| 应用连错库 | `/api/v1/meta` 中 bucket/env 不符 | 核对 `DATABASE_URL`、`APP_ENV` |

### 6.5 磁盘写满

```bash
df -h /data
docker system df -v | head -30
du -sh /data/docker/containers/* | sort -h | tail -10
```

处置顺序：清理过期备份 → `docker image prune -f` → `docker builder prune -f` → 清理异常大日志容器 → 扩容磁盘。

### 6.6 Grafana 无数据 / 日志查不到

```bash
docker compose --env-file .env logs --tail=100 prometheus loki promtail
docker compose --env-file .env exec prometheus wget -qO- http://backend:8080/actuator/prometheus | head
```

| 根因 | 判据 | 处置 |
|---|---|---|
| 抓取目标 down | Prometheus Targets 页显示 down | 检查 monitor 网络、backend 是否 healthy |
| Promtail 读不到日志 | `logs promtail` 报 permission/路径不存在 | 确认宿主为 Linux 且路径存在 |
| Promtail 容器 `unhealthy` | healthcheck 失败 | 本编排已用 `bash -c 'exec 3<>/dev/tcp/127.0.0.1/9080'` 探测；若仍失败看 `logs promtail` |
| Loki 报 `400 entry too far behind` | 宿主机存在其它业务栈的历史日志 | 已在采集端 `drop older_than: 24h`；确认 `promtail-config.yml` 生效 |
| 保留期过短 | 查询历史为空 | 调整 Loki `retention_period` |

### 6.7 升级失败

```bash
docker compose --env-file .env ps
docker compose --env-file .env logs --tail=200 backend
grep -E 'IMAGE' .env
```

处置：把 `.env` 中镜像 tag 回退为上一版本 → `docker compose --env-file .env up -d --no-deps backend frontend` → `verify.sh` 复核。数据卷不受镜像回退影响。

### 6.8 MinIO 拉取失败 / 启动即退出（官方镜像下架、CPU 基线不兼容）

```bash
docker compose --env-file .env logs --tail=100 minio
docker image ls | grep minio
docker run --rm minio/minio:RELEASE.2024-12-18T13-15-44Z --version
```

| 根因 | 判据 | 处置 |
|---|---|---|
| 官方镜像已下架 | 拉取 `403/404`，或 `manifest unknown` | 按手册 15.2 从 `bitnamilegacy` 提取二进制本地构建，并打回 `.env` 中的 tag |
| CPU 不支持 x86-64-v2 | 日志 `Fatal glibc error: CPU does not support x86-64-v2` | 使用 2024-12 版本二进制（本地构建），勿用 2025+ 官方/第三方新版镜像 |
| 镜像 tag 与 `.env` 不一致 | compose 重新去远端拉取并失败 | 本地构建镜像 tag 必须与 `MINIO_IMAGE` / `MC_IMAGE` 完全一致 |
| 宿主机迁移后镜像缺失 | `docker image ls` 无对应镜像 | 源机 `docker save` → 目标机 `docker load`（见手册 15.2） |

## 七、变更管理要求

| 变更类型 | 审批 | 窗口 | 回滚方式 |
|---|---|---|---|
| 应用镜像升级 | 技术负责人 | 低峰期 | 回退镜像 tag |
| 配置/变量调整 | 技术负责人 | 随时（需通知） | 恢复 `.env` 旧值 |
| 中间件版本升级 | 架构组 + 变更单 | 计划窗口 | 保留旧数据卷快照 |
| 编排结构变更 | 架构组评审 | 计划窗口 | `git revert` 后重建 |
| 密钥轮换 | 安全负责人 | 计划窗口 | 双人复核，保留旧密钥 24h |

变更前后必须执行：`verify.sh` → 变更 → `verify.sh --full`，并在变更单记录结果。

## 十、红线清单（禁止操作）

1. 禁止在生产执行 `docker compose down -v`。
2. 禁止在 `docker-compose.yml` 中写入明文密码或密钥。
3. 禁止使用 `latest` 镜像 tag 部署。
4. 禁止将中间件端口映射到 `0.0.0.0`。
5. 禁止未经校验的备份直接用于恢复（必须先 `sha256sum -c`）。
6. 禁止在未执行 `verify.sh` 的情况下宣布变更完成。
7. 禁止将 `.env`、备份文件提交到代码仓库或工单附件。
8. 禁止用宿主侧 `docker kill` 作为自愈演练手段（Docker 29+ 不触发 restart 策略），演练统一使用 `docker exec <容器> kill -TERM 1`。
